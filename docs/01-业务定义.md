# 01 · 业务定义

> 版本:v1.0 · 状态:已定稿
> 本文档定义「面向社区用户的生活服务平台」的角色、业务域、核心规则与状态机。后续接口、表结构、代码均以此为源。

---

## 1. 角色模型

### 1.1 三类角色

| 角色 | 标识 | 能力 |
|---|---|---|
| 普通用户 | `USER` | 浏览、下单、发内容、签到、使用 AI 客服 |
| 商户 | `MERCHANT` | 拥有 `USER` 全部能力 + 店铺/商品/订单管理 + 商户端 AI 客服 |
| 管理员 | `ADMIN` | 商户审核、内容审核、数据看板 |

### 1.2 账号模型

**一张账号表 + 角色字段。**

```
tb_user
├── id
├── phone           唯一
├── password        预留字段(当前为验证码登录,不存密码)
├── nickname
├── avatar
├── role            USER / MERCHANT / ADMIN
└── status          ACTIVE / DISABLED
```

- 一个手机号只能注册一个账号。
- 用户申请成为商户,**审核通过后 `role` 由 `USER` 升级为 `MERCHANT`**,不新建账号。
- `MERCHANT` 天然包含 `USER` 的全部权限;鉴权时按「角色等级」判断,不做多角色集合。
- 管理员账号不开放注册,由初始化脚本或运维创建。

> 设计理由:用户和商户本质是同一个人的不同身份。拆成两套账号会导致同手机号重复注册、重复登录、订单归属混乱。

### 1.3 鉴权方式

- 登录成功后签发 **JWT**:
  - `accessToken` 有效期 30 分钟
  - `refreshToken` 有效期 7 天
- 请求头:`Authorization: Bearer <accessToken>`
- 统一拦截器负责:解析 token → 写入 `UserContext`(ThreadLocal)→ 请求结束清理。
- 角色校验通过注解完成,例如 `@RequireRole(MERCHANT)`。

## 3. 核心业务规则

### 3.1 账号与权限

1. 手机号 + 短信验证码登录;验证码 5 分钟有效,同一手机号 60 秒内只能发送一次。
2. 首次登录自动注册,默认角色 `USER`。
3. 同一手机号连续 5 次验证码错误,锁定 10 分钟。
4. 被禁用的账号(`DISABLED`)登录返回 `2004`。
5. 用户只能修改自己的资料;管理员可禁用账号。

### 3.2 商户入驻

1. 提交材料:店铺名称、营业执照号、经营地址、联系人、联系电话。
2. 同一用户同一时间只能有一条 `PENDING` 申请。
3. 管理员审核:
   - `APPROVED` → 创建店铺、用户 `role` 升级为 `MERCHANT`
   - `REJECTED` → 记录驳回原因,用户可修改后重新提交
4. 审核通过后,店铺默认状态为 `OPEN`,可随时 `CLOSED`(暂停营业)。

### 3.3 店铺与商品

1. 一个商户对应一个店铺(首期一人一店)。
2. 商品字段:名称、价格、库存、图片、描述、状态。
3. 价格单位:**分(Long)**,禁止使用浮点数。
4. 商品状态:`ON_SALE`(在售)/ `OFF_SALE`(下架)。
5. 只有 `ON_SALE` 且库存 > 0 的商品可被下单。
6. 商户只能操作自己店铺下的商品。

### 3.4 交易(普通订单)

1. 下单校验顺序:商品存在 → 在售 → 库存充足 → 用户状态正常。
2. 订单创建时**扣减库存**,使用数据库乐观锁(`version`)或 `stock >= n` 条件更新。
3. 订单 30 分钟未支付,由延迟队列自动关闭并回滚库存。
4. 订单必须幂等:`Idempotency-Key` 相同则返回同一订单。
5. 金额计算:`totalAmount = Σ(price × quantity)`,全程使用 Long(分)。
6. 订单所属店铺与商品所属店铺必须一致(首期一单一店)。

### 3.5 优惠券秒杀

1. 商户创建优惠券:面额、售价、总量、开始/结束时间、每人限购。
2. 抢购分两步:
   - **申请令牌**:校验活动时间、用户资格,发放一次性令牌(Redis,60 秒有效)。
   - **提交抢购**:携带令牌,进入 Lua 原子扣减。
3. Lua 脚本内依次完成:
   - 校验令牌有效且未使用
   - 校验库存 > 0
   - 校验一人一单(用户集合)
   - 扣减库存
   - 写入用户购买标记
4. 扣减成功后投递 Kafka,异步创建订单。
5. 消费端幂等:`voucher_id + user_id` 唯一索引 + 消息幂等键。
6. 定时对账:Redis 库存与 DB 订单数量比对,差异进入补偿。
7. 秒杀开始前入口限流:令牌桶,按全局 QPS 与用户维度双重限流。

### 3.6 内容社区

1. 笔记字段:标题、正文、图片列表、关联店铺(可选)、状态。
2. 笔记状态:`PUBLISHED` / `HIDDEN`(管理员隐藏)/ `DELETED`。
3. 点赞:有序集合 `ZSet`,分数为时间戳,支持点赞排行榜。
4. 收藏:集合 `Set`,支持"我的收藏"分页。
5. 评论:支持一级评论与二级回复,默认只展示未隐藏评论。
6. 关注:用户 A 关注 B 后,B 发布新笔记写入 A 的 Feed 收件箱(`ZSet`)。
7. Feed 采用**推拉结合**:
   - 普通作者(粉丝数 < 1000):发笔记时推送到粉丝收件箱 `clp:feed:user:{userId}`
   - 大 V(粉丝数 >= 1000):不推送,只写自己的发件箱 `clp:outbox:user:{userId}`
   - 读取时合并"自己的收件箱"和"关注的大 V 发件箱",按时间倒序、按 blogId 去重
   - 阈值配置:`clp.feed.big-v-threshold`
8. 作者只能删除自己的笔记;管理员可隐藏任意笔记。
9. 推拉结合的取舍:大 V 避免了写扩散风暴,代价是读取时多一次发件箱拉取;普通用户仍然享受推送的低延迟。

### 3.7 签到与积分

1. 签到数据:**Redis Bitmap**,key = `sign:{userId}:{yyyyMM}`,offset = 当月第几天 - 1。
2. 每日签到 +5 积分。
3. 连续签到 7 天,第 7 天额外 +20 积分;中断后重新计算。
4. 同一天重复签到返回 `9001`,不重复加分。
5. 积分变动必须写流水表 `tb_point_log`,记录变动值、变动后余额、来源、业务 ID。
6. 签到成功后异步落库 `tb_sign`,用于统计与补偿;Redis 为准,DB 为审计。

### 3.8 实时通知

1. 通知触发场景:
   - 用户下单 → 通知商户
   - 商户接单 / 完成订单 → 通知用户
   - 秒杀成功 / 失败 → 通知用户
   - 商户审核结果 → 通知用户
   - 系统公告 → 通知指定角色
2. 传输:业务事件 → Kafka → 通知消费者 → WebSocket 推送。
3. 用户在线:直接推送;离线:落库 `tb_notification`,上线后拉取未读。
4. 多实例部署:通过 Redis Pub/Sub 做跨节点广播。
5. 未读数提供单独接口,避免拉全量列表。

### 3.9 AI 客服

#### 用户端

可回答:
- 平台使用问题
- 本社区/店铺最近上架的商品
- 自己的订单状态
- 平台公告
- 天气(外部 API)

#### 商户端

可回答:
- 自己店铺的商品与库存
- 自己店铺的订单
- 简单经营数据(今日订单数、销售额)

#### 强制规则

1. **数据权限在服务端工具层收口**:工具调用时注入当前登录的 `userId` / `shopId`,不接受大模型传入的用户标识。
2. 用户端 Agent **不得**查询其他用户的数据;商户端 Agent **不得**查询其他店铺的数据。
3. 每个用户每分钟最多 20 次 AI 请求,超限返回 `1003`。
4. 会话记录落库,用于审计与后续优化。
5. AI 服务不可用时降级为固定话术 + 人工客服入口,不能让主链路报错。

## 4. 状态机

### 4.1 订单

```
                    ┌──────────┐
                    │ CREATED  │  待支付
                    └────┬─────┘
         支付成功         │        30 分钟未支付
      ┌──────────────────┼──────────────────┐
      ▼                  │                  ▼
┌──────────┐             │             ┌──────────┐
│   PAID   │             │             │  CLOSED  │
└────┬─────┘             │             └──────────┘
     │ 商户接单           │ 用户取消
     ▼                   ▼
┌──────────┐        ┌──────────┐
│ ACCEPTED │        │CANCELLED │
└────┬─────┘        └──────────┘
     │ 商户完成
     ▼
┌───────────┐
│ COMPLETED │  终态
└───────────┘
```

| 当前状态 | 允许动作 | 目标状态 |
|---|---|---|
| CREATED | 支付 | PAID |
| CREATED | 取消 | CANCELLED |
| CREATED | 超时 | CLOSED |
| PAID | 商户接单 | ACCEPTED |
| PAID | 退款(预留) | REFUNDED |
| ACCEPTED | 完成 | COMPLETED |
| COMPLETED | — | 终态 |
| CANCELLED / CLOSED / REFUNDED | — | 终态 |

### 4.2 商户入驻申请

```
PENDING ──通过──> APPROVED
   │
   └──驳回──> REJECTED ──重新提交──> PENDING
```

### 4.3 优惠券

```
DRAFT ──发布──> PUBLISHED ──结束时间到──> ENDED
```

`RUNNING` / `SOLD_OUT` 由时间与库存实时计算,不落库。

### 4.4 笔记

```
DRAFT ──发布──> PUBLISHED ──管理员隐藏──> HIDDEN
                    │
                    └──作者删除──> DELETED
```

### 5.1 关键约束

- `tb_user.phone` 唯一索引
- `tb_product.stock >= 0` 检查约束 + `version` 乐观锁
- `tb_voucher_order(voucher_id, user_id)` 唯一索引(一人一单兜底)
- `tb_order.order_no` 唯一索引(幂等兜底)
- `tb_point_log` 只增不改
- 所有金额字段为 `BIGINT`,单位分

## 6. 非功能要求

| 维度 | 要求 |
|---|---|
| 接口响应 | P95 < 300ms(非 AI、非秒杀链路) |
| 秒杀 | 单机压测目标 1000 QPS,不超卖、不重复 |
| AI 客服 | 首字节 < 2s,超时 15s |
| 一致性 | 秒杀链路最终一致,允许秒级延迟 |
| 可用性 | 单机部署;中间件故障时主链路降级而非雪崩 |
| 安全 | JWT 签名;短信验证码登录;所有写接口校验归属 |
| 日志 | 关键链路带 traceId;敏感字段脱敏 |

## 7. 业务边界(首期不做)

- 不做真实支付,支付接口为模拟回调。
- 不做退款流程,仅预留状态。
- 不做多商户购物车、跨店合并下单。
- 不做实时聊天(用户 ↔ 商户),只做系统通知。
- 不做推荐算法,Feed 仅按关注 + 时间排序。
- 不做分库分表(参考项目有能力,但本项目首期单库)。
