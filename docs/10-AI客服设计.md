# AI 客服设计

> 相关接口见 [03-接口清单.md](03-接口清单.md#11-ai-客服)，表结构见 [04-数据模型.md](04-数据模型.md#7-ai-客服)。

## 1. 目标与范围

为平台的用户端与商户端各提供一个 AI 助手：

- **用户端**：订单、优惠券、秒杀、积分、店铺与商品咨询。
- **商户端**：本店订单、商品库存、经营数据、店铺信息。

两端共用一套会话与消息存储，通过 `scope` 区分；系统提示词、可用工具不同。

实现分四阶段：

| 阶段 | 内容 | 状态 |
|---|---|---|
| A | 会话持久化、提示词工程、DeepSeek 对话、限流 | 已完成 |
| B | Tool / Function Calling | 已完成 |
| C | RAG（双路召回 + RRF + rerank + 证据过滤） | 已完成 |
| D | 上下文拼接、摘要记忆、会话锁、超时/熔断/降级、RAG 评估 | 已完成 |

## 2. 分层

```
Controller  AiChatController            协议、参数校验、取 UserContext
    │
Service     AiChatServiceImpl           限流、归属校验、历史、落库、编排
    │
Gateway     AiChatGateway               模型调用边界，屏蔽 Spring AI 细节
    │       SpringAiChatGateway
    │
Tools       AiToolFactory               按身份创建工具实例
            UserAiTools / MerchantAiTools
    │
Domain      IOrderService / IProductService / IShopService / IGrowthService
    │
Model       OpenAiChatModel → DeepSeek（OpenAI 兼容协议）
Vector      ZhipuEmbeddingClient / ZhipuRerankClient（RAG 检索）
```

模块归属：

- `clp-framework-ai`：智谱 embedding / rerank 客户端，与业务无关。
- `clp-parameter/ai`：请求与响应 record，纯契约。
- `clp-core-service/ai`：会话、提示词、工具、编排。

## 3. 数据模型

```sql
tb_ai_conversation(id, user_id, scope, title, last_message_at, created_at, updated_at)
tb_ai_message(id, conversation_id, role, content, tool_calls JSON, tokens_in, tokens_out, created_at)
```

设计要点：

- 消息一条一行，支持分页、审计、按消息统计 token。
- `tool_calls` 存工具调用审计：工具名、参数摘要、结果、耗时。
- `scope` 只在会话上，消息不重复存。
- 会话列表按 `updated_at` / `last_message_at` 倒序。

## 4. Phase A：对话链路

```
POST /api/v1/ai/conversations/{id}/messages
  → JWT 拦截器写入 UserContext
  → 参数校验（非空、≤2000 字）
  → Redis 固定窗口限流：clp:ai:chat:rate:{userId}，20 次/分钟
  → 校验会话归属（不存在与不属于统一返回 10001）
  → 取最近 20 条历史（倒序取、反转）
  → 落库 user 消息
  → 更新会话标题（首条消息前 20 字）与 last_message_at
  → 系统提示词 + 历史 + 当前问题 → DeepSeek
  → 落库 assistant 消息（token 统计）
  → 更新会话 last_message_at 为回复时间
```

关键取舍：

- 模型调用不放在事务里，避免长时间占用数据库连接。
- 历史在插入当前消息之前读取，防止当前问题重复。
- 系统提示词放在 `resources/prompts/*.txt`，改提示词不用改代码。
- 会话不存在与越权统一 10001，避免枚举他人会话 ID。

## 5. Phase B：工具调用链路

```
AiChatServiceImpl
  → new AiToolRecorder()                    本次请求的调用记录
  → AiToolFactory.create(scope, userId, recorder)
       USER     → new UserAiTools(userId, ...)
       MERCHANT → 查 Merchant → 查 Shop → new MerchantAiTools(merchantId, shopId, ...)
  → AiChatCommand(scope, history, question, tools)
  → SpringAiChatGateway
       ChatClient.prompt().system(...).messages(...).user(...).tools(tools...)
       Spring AI 自动执行 tool_calls 并把结果回传模型
  → assistant 消息写入 tool_calls JSON
```

### 安全约束

1. **身份不来自模型**：`userId` / `merchantId` / `shopId` 在构造工具时注入，工具方法参数里没有这些字段。
2. **归属条件进 SQL**：用户查订单用 `orderNo + userId` 联合条件，查不到统一按不存在处理。
3. **工具只读**：当前阶段所有工具都是查询，不提供取消订单、改价、改库存等写操作。
4. **失败不抛异常**：工具返回 `ToolResponse{success=false, message}`，让模型能解释原因而不是中断对话。
5. **结果限量**：单次最多 10 条，单轮最多记录 20 次工具调用。

### 工具清单

| 工具 | 端 | 身份来源 |
|---|---|---|
| `queryMyOrders` / `queryMyOrderDetail` / `queryMyPoints` | 用户端 | `userId` |
| `searchShops` / `listShopProducts` / `queryShopInfo` | 用户端 | 无身份，公开数据 |
| `queryMyShop` / `queryShopOrders` / `queryShopProducts` / `queryShopStats` | 商户端 | `merchantId` + `shopId` |

## 7. 错误码

| code | 含义 |
|---|---|
| 10001 | 会话不存在或不属于当前用户 |
| 10002 | 当前角色无权使用该助手 |
| 10003 | 消息内容过长 |
| 10004 | AI / 向量 / 重排服务不可用 |
| 10005 | 会话正在处理中（Phase D 会话锁） |
| 1003 | 单用户每分钟限流 |

## 9. 后续阶段

### Phase C：RAG（已完成）

#### 检索链路

```
query
 → 归一化 + SHA-256
 → 命中 RAG 结果缓存则直接返回
 → 查询向量缓存（1h）→ 未命中则调用 embedding-3
 → 向量召回: scope 内最多 200 个分片, Java 侧余弦相似度
 → 关键词召回: MySQL ngram FULLTEXT, 最多 20 条
 → RRF 融合: score = Σ 1/(60 + rank), 取前 10
 → rerank-pro 精排: 取前 4, 分数阈值 0.35
 → 证据拼接: 最多 2000 字
 → 带编号写入系统提示词
```

#### 降级策略

| 故障 | 降级 |
|---|---|
| embedding 不可用 | 只走关键词召回 |
| 全文索引不可用 | 关键词通道退化为 LIKE |
| rerank-pro 不可用 | 使用 RRF 排序结果 |
| 任意检索异常 | 返回空证据,对话继续 |

#### 知识入库

- 启动时导入 `classpath:knowledge/*.md`；`user-` / `merchant-` 前缀决定 scope，其余为 ALL。
- 按 Markdown 标题划章节，章节内按段落累积，单分片默认不超过 600 字。
- 用 SHA-256 增量导入：只对新分片调用 embedding，内容变更时删除过期分片。
- 管理端接口：`POST /api/v1/admin/ai/knowledge` 导入/更新，`DELETE /api/v1/admin/ai/knowledge/{docId}` 删除。

#### 缓存

| Key | 内容 | TTL |
|---|---|---|
| `clp:ai:embedding:query:{sha256}` | 查询向量 | 1h |
| `clp:ai:rag:result:{scope}:{sha256}` | 最终证据集合 | 5m |

进程内 `KnowledgeVectorCache` 缓存分片向量，知识变更时清空。

#### 已知边界

- RAG 结果缓存 5 分钟，刚导入的知识最多 5 分钟后生效。
- 进程内向量缓存是单机语义，多节点部署需要额外的失效机制。
- Java 余弦适合千级分片；数据量增大后应替换为专业向量库。
- rerank 普通版对短文本区分度低，统一使用 `rerank-pro`。

### Phase D：上下文与可靠性（已完成）

#### 1. 上下文拼接

每次调用的系统提示词按顺序拼接：

```
基础提示词（角色 / 职责 / 事实约束 / 工具使用 / 安全）
  + 历史对话摘要（如果有）
  + RAG 参考资料（如果有；没有则明确告知"本轮未检索到资料"）
```

最近 `history-window`（默认 20）条消息仍以原文进入 messages；更早的内容由摘要承载。

#### 2. 摘要记忆

- 表字段：`tb_ai_conversation.summary`、`summary_message_id`。
- 触发条件：未摘要消息数 > `summary-trigger-messages`（默认 30）。
- 每次最多把「未摘要消息数 - 最近窗口」条旧消息合并进摘要，最近窗口保持原文。
- 摘要由同一个大模型生成，提示词要求保留：用户诉求、已确认事实、已给方案、未解决问题。
- 摘要失败时保留旧摘要且不推进 `summary_message_id`，下次继续尝试。
- 摘要调用同样有超时（复用 `timeout-ms`），避免拖住主请求。

> 代价：触发摘要的那一次请求会多一次模型调用，实测一次问答约 18 秒。属于每 30 条消息一次的偶发成本。

#### 3. 会话锁

- Redisson 锁：`clp:ai:conversation:lock:{conversationId}`。
- `tryLock(0, 60s)`，抢不到直接返回 `10005`。
- 锁粒度为会话，不同会话互不影响；租约到期自动释放，避免死锁。

#### 4. 超时

- 模型调用提交到虚拟线程执行器，`Future.get(timeout-ms)` 设置硬超时（默认 15s）。
- 超时后取消任务，按失败计入熔断器。

#### 5. 熔断与降级

```
CLOSED --连续失败达到阈值--> OPEN --冷却结束--> HALF_OPEN
   ^                                              │
   └──────────── 探测成功 ─────────────────────────┘
                 探测失败 → OPEN
```

- 阈值默认 5 次，冷却 30s，半开只放一个探测请求。
- 熔断打开期间，业务层在检索之前直接返回固定话术，不再消耗 embedding / rerank / 模型调用。
- 降级回复仍然落库，响应 `degraded=true`，`sources` 为空。
- 降级话术：`抱歉,AI 助手暂时不可用,请稍后再试。您也可以联系人工客服(每天 9:00-21:00)。`

#### 6. RAG 评估

- 接口：`POST /api/v1/admin/ai/rag/evaluate`（ADMIN）。
- 指标：
  - **HitRate**：期望文档出现在最终证据中的用例占比；
  - **MRR**：首次命中名次的倒数均值。
- 样例集：`loadtest/rag-eval-user.json`（10 条）、`loadtest/rag-eval-merchant.json`（6 条）。
- 实测：用户端 10/10，HitRate 1.0，MRR 1.0；商户端 6/6，HitRate 1.0，MRR 1.0。

#### 7. 已知边界

- 熔断器是进程内状态，多节点各自独立。
- 摘要同步生成，触发时该次请求延迟明显增加；后续可改为回复后异步生成。
- 目前没有 SSE 流式输出，超时约束的是整轮调用，不是首包。
