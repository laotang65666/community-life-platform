## 2. 依赖方向

```
                    ┌──────────────┐
                    │ clp-common   │
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
┌───────▼──────┐  ┌────────▼───────┐  ┌───────▼────────┐
│clp-parameter │  │clp-id-generator│  │ framework-*    │
└───────┬──────┘  └────────┬───────┘  └───────┬────────┘
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                  ┌────────▼─────────┐
                  │ clp-core-service │
                  └──────────────────┘
```

### 2.1 硬性规则

| 规则 | 说明 |
|---|---|
| `clp-common` 不依赖任何业务模块 | 它是地基 |
| `clp-parameter` 只依赖 `clp-common` | 纯 DTO,不引框架 |
| `framework-*` 之间**不互相依赖** | 需要组合时在 `core-service` 编排 |
| `framework-*` 只依赖 `clp-common` | 保持可插拔 |
| `clp-core-service` 依赖所有模块 | 唯一的组装点 |
| **禁止循环依赖** | 父 POM 不设置 `allow-circular-references` |

### 2.2 为什么框架模块不互相依赖

- `framework-mq` 不应知道 `framework-redis` 的存在
- 需要"发消息 + 写缓存"时,在 `core-service` 的 Service 里编排
- 否则模块会逐渐纠缠成一个单体大泥球

## 3. 业务模块内部结构

以 `order` 为例:

```
com.laotang.core.order
├── controller/
│   └── OrderController.java
├── service/
│   ├── OrderService.java              接口
│   └── impl/
│       └── OrderServiceImpl.java      实现
├── mapper/
│   └── OrderMapper.java
├── entity/
│   ├── Order.java
│   └── OrderItem.java
├── dto/
│   ├── CreateOrderRequest.java
│   ├── OrderResponse.java
│   └── OrderQuery.java
├── converter/
│   └── OrderConverter.java            entity ↔ dto
├── event/
│   └── OrderCreatedEvent.java
└── enums/
    └── OrderStatus.java
```

### 3.1 分层职责

| 层 | 职责 | 禁止 |
|---|---|---|
| Controller | 参数校验、调用 Service、返回 Result | 写业务逻辑、直接调 Mapper |
| Service | 业务编排、事务边界、权限校验 | 返回 Entity 给 Controller |
| Mapper | 单表 CRUD、简单查询 | 写业务判断 |
| Converter | Entity ↔ DTO | 写业务逻辑 |

### 3.2 跨模块调用

- 允许:`order` 调 `product` 的 **Service 接口**(通过 `IProductService`)
- 禁止:`order` 直接注入 `ProductMapper`
- 禁止:跨模块访问对方的 `entity`(用 DTO)

> 这条规则是为了将来拆微服务时,接口天然就是服务边界。

## 4. 包命名

```
com.laotang
├── clp.common.
├── clp.parameter.
├── clp.framework.redis.
├── clp.framework.lock.
├── clp.framework.mq.
```

- 全小写,不用下划线
- 按**业务域**分包,不按技术层分包
- 领域内再按 `controller / service / mapper / entity / dto` 分层

## 5. 编码约束

### 5.1 分层

| 约束 | 值 |
|---|---|
| 单个方法 | < 50 行 |
| 单个类 | < 500 行 |
| 单个文件 | < 800 行 |
| 嵌套层级 | ≤ 4 |
| 圈复杂度 | ≤ 10 |

### 5.2 不可变

- DTO / VO 使用不可变对象(`record` 或 `final` 字段 + 全参构造)
- 禁止在 Service 中修改入参对象
- 集合返回使用 `List.copyOf()` / `Collections.unmodifiableList()`

### 5.3 异常

- 业务异常统一抛 `BusinessException(code, message)`
- 全局异常处理器统一转 `Result`
- **禁止吞异常**,`catch` 后必须记录日志或重新抛出
- 日志必须带 `traceId` 和关键业务 ID

### 5.4 事务

- 事务边界只放在 Service 层
- `@Transactional(rollbackFor = Exception.class)`
- **禁止在事务中做远程调用**(Kafka、HTTP、LLM)
- 外部调用放到事务提交后(`TransactionSynchronization`)

### 5.5 缓存

- 缓存 key 统一由 `RedisKey` 常量类生成,禁止硬编码字符串
- 写操作必须考虑缓存失效顺序:**先更新 DB,再删缓存**
- 空值缓存 TTL ≤ 2 分钟

### 5.6 幂等

- 所有写接口评估是否需要幂等
- 下单、秒杀、签到必须有唯一约束兜底
- 幂等键统一存 `tb_idempotency`

### 5.7 安全

- 所有写操作校验数据归属(`userId` / `shopId`)
- 禁止直接把请求参数当查询条件拼 SQL
- 密码、手机号、token 日志脱敏
- AI 工具调用只接受服务端注入的身份

## 7. 构建配置

### 7.1 父 POM 禁止项

```xml
<!-- 不要出现 -->
<configuration>
    <allow-circular-references>true</allow-circular-references>
</configuration>
```

出现循环依赖说明分层已坏,应该修依赖,不是绕过。

### 7.2 必须开启

| 配置 | 作用 |
|---|---|
| `maven-compiler-plugin` | 统一 JDK 21 |
| `jacoco-maven-plugin` | 覆盖率报告 |
| `maven-surefire-plugin` | 单元测试 |
| `maven-failsafe-plugin` | 集成测试(`*IT.java`) |
| `maven-enforcer-plugin` | 禁止循环依赖、统一版本 |

### 7.3 环境隔离

```
application.yml           公共配置
application-local.yml     本地
application-test.yml      测试
application-prod.yml      生产
```

- 敏感配置用环境变量,禁止提交密码
- 数据源、Redis、Kafka 地址按 profile 区分

## 8. 新模块接入清单

新增一个业务模块时,逐项确认:

- [ ] 在 `core.<domain>` 下建包
- [ ] 只依赖 `Service` 接口,不依赖其他模块的 `Mapper` / `entity`
- [ ] DTO 放本模块 `dto`,跨模块传输用它
- [ ] 写操作有权限校验
- [ ] 需要幂等的接口有唯一约束
- [ ] 缓存 key 用常量类
- [ ] 抛业务异常,不返回 `null` 表示错误
- [ ] 补充单元测试(Service 层优先)
- [ ] 更新 `03-接口清单.md`
