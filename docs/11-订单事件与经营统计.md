# 订单事件与经营统计

> 相关表结构见 [04-数据模型.md](04-数据模型.md#81-订单事件与经营统计)，接口见 [03-接口清单.md](03-接口清单.md)。

## 1. 要解决的问题

商户报表和管理看板如果直接对 `tb_order` 做实时聚合，会有两个问题：

1. 订单表越来越大，每次看板都全表/大范围扫描；
2. 交易链路和统计链路耦合，统计慢会拖累查询。

所以把统计拆成一条异步数据链路：

```
交易写入(强一致)
   → Outbox(同事务)
   → Kafka
   → 统计消费者(幂等)
   → tb_shop_daily_stats
   → 商户报表 / 管理看板
```

当天数字仍查实时表保证准确，历史趋势查聚合表保证性能。

## 2. 事件生产：Outbox 与业务同事务

订单状态变更都在 `OrderTxService` 的 `@Transactional` 方法里：

```java
@Transactional
public void pay(Long orderId, Long userId) {
    ...
    orderEventPublisher.publish(OrderEventType.ORDER_PAID, order);
}
```

`publish` 内部走 `OutboxService.enqueue`，把事件写进 `tb_outbox`。
因为和订单更新在同一个事务里，**订单成功则事件一定入库，订单回滚则事件一起回滚**。

之后由 `OutboxService.dispatch()` 每秒扫描 PENDING 消息投递 Kafka：

- Kafka key = `messageId`，保证同一事件落到同一分区；
- 投递成功改 SENT，消费成功改 ACKED；
- 条件更新（`status = PENDING`）防止消费端 ACKED 被覆盖。

## 3. 事件类型与统计口径

| 事件 | 触发点 | 统计增量 |
|---|---|---|
| `ORDER_CREATED` | 下单成功 | `order_count + 1` |
| `ORDER_PAID` | 支付成功 | `paid_count + 1`，`gmv + amount` |
| `ORDER_ACCEPTED` | 商户接单 | 无(状态流转,不重复计数) |
| `ORDER_COMPLETED` | 商户完成 | `completed_count + 1` |
| `ORDER_CANCELLED` | 用户取消 | `cancel_count + 1` |
| `ORDER_CLOSED` | 超时关闭 | `close_count + 1` |

**统计日期取订单创建日**（`orderCreatedAt`），而不是事件发生日。
这样"今日订单 / 今日成交额"和实时 SQL 的口径一致：昨天创建、今天支付的订单仍算昨天。

## 4. 消费幂等

Kafka 至少一次投递，重复消息必须有兜底。

消费者先写 `tb_order_event_log`：

```sql
INSERT IGNORE INTO tb_order_event_log (..., event_id, ...)
```

- `uk_event_id` 唯一索引；
- 返回 0 表示重复事件，直接返回；
- 去重记录和日统计累加在**同一个事务**里：累加失败会连去重记录一起回滚，Kafka 重试仍能重新处理。

日统计用唯一键 `(shop_id, stat_date)` + `ON DUPLICATE KEY UPDATE` 累加，天然支持多分区并发消费。

## 5. 查询口径

### 商户经营报表

`GET /api/v1/shops/{shopId}/stats?days=7`（商户本人）

- `today`：直接查 `tb_order`，包含今日订单数、成交订单数、成交额、待接单数；
- `trend`：查 `tb_shop_daily_stats`，按天返回下单/支付/完成/取消/关闭/GMV。

### 管理看板

`GET /api/v1/admin/dashboard/summary`（ADMIN）

- 用户数、商户数、店铺数、待审核商户数：实时 count；
- 今日订单数、今日成交额：实时查订单表；
- `last7Days`：平台维度日统计（按 `stat_date` 汇总所有店铺）。

## 6. 一致性说明

| 维度 | 行为 |
|---|---|
| 交易 → 事件 | 同事务，强一致 |
| 事件 → Kafka | 最多 1 秒延迟（Outbox 定时投递），失败重试 |
| Kafka → 统计表 | 秒级延迟；消费失败不 ACK，靠重试 |
| 当天报表 | 实时表，不受消费延迟影响 |
| 历史趋势 | 聚合表，允许秒级延迟 |

## 7. 实测记录（2026-10-17）

| 场景 | 结果 |
|---|---|
| 下单 + 支付 | Outbox 2 条 ACKED；事件日志 CREATED/PAID；日统计 `1/1/3980` |
| 重放同一事件 | `tb_order_event_log` 仍为 2 条，日统计仍为 `1/1/3980`（幂等生效） |
| 接单 + 完成 + 取消 | 事件日志 `ACCEPTED/COMPLETED/CANCELLED` 各 1；日统计 `2/1/1/1/0/3980` |
| 3 秒超时关单 | 订单变 CLOSED，`ORDER_CLOSED` 事件落库，`close_count + 1` |
| 商户报表 | today `5 单 / 3 成交 / 89.60 元 / 1 待接单`；trend 来自聚合表 |
| 管理看板 | 1027 用户 / 1 商户 / 1 店铺 / 今日 5 单 / 8960 分 / 1 待审核 |

## 8. 已知边界与后续

- 日统计从功能上线开始累积，**历史订单没有回填**；如需历史趋势，应补一个一次性回填任务。
- GMV 按订单创建日归属，不是按支付日；如果财务口径要求按支付日，需要新增 `paid_date` 维度。
- 当前消费者直接写 MySQL，规模增大后可替换为 Flink/Spark 写入数据湖，再同步到报表库。
- 日统计表只保留按天粒度；需要小时级可以再加 `stat_hour` 或独立实时数仓。
