# 09 · 秒杀链路详解

> 版本:v1.0
> 这一篇不只是"用了什么",而是逐段解释"为什么这么做"。
> 对应代码:`core.marketing`、`core.outbox`、`core.reconcile`、`lua/seckill.lua`。

---

## 1. 秒杀到底难在哪

普通下单和秒杀的区别,不是"接口多一个",而是**流量形态完全不同**:

| 维度 | 普通下单 | 秒杀 |
|---|---|---|
| 流量 | 平缓 | 瞬时洪峰(几千 QPS) |
| 库存 | 充足 | 极少,抢完即止 |
| 正确性 | 不能超卖 | 不能超卖 + 不能一人多单 |
| 响应 | 同步落库 | 必须异步削峰 |
| 失败代价 | 重试即可 | 超卖 = 资损,重复 = 客诉 |

所以秒杀的设计目标只有四个字:**挡住 + 算对**。

- **挡住**:绝大多数无效请求在到达数据库之前就被拦掉。
- **算对**:库存不超卖、一人一单、消息不丢不重。

## 2. 总体架构:五道防线

```
用户请求
   │
   ▼
① 限流          令牌接口 5 次/秒/用户
   │
   ▼
② 令牌          一次性令牌,60 秒有效
   │
   ▼
③ Redis + Lua   原子完成:令牌校验 + 一人一单 + 库存扣减
   │
   ├─ 失败 → 直接返回 7003/7004/7005,不碰数据库
   │
   ▼ 成功
④ Outbox        消息先写库(PENDING),再由定时器投递
   │
   ▼
⑤ Kafka         异步削峰,消费者按自己的速度落库
   │
   ▼
   订单表 + 审计库存 + 对账
```

**记住这张图,面试时就是你的主线。**

## 3. 完整时序

### 3.1 商户创建秒杀券

```
POST /api/v1/vouchers
  ├─ 校验店铺归属(shop.merchantId == 当前商户)
  ├─ 校验时间窗口(end > begin)
  ├─ INSERT tb_voucher          (type=SECKILL, status=PUBLISHED)
  ├─ INSERT tb_seckill_voucher  (stock, initial_stock, per_user_limit)
  └─ 预热 Redis
       SET clp:seckill:stock:{voucherId} = stock
       DEL clp:seckill:users:{voucherId}
```

**为什么预热:** 秒杀开始时不能再去查数据库初始化库存,必须在活动前就把库存放进 Redis。

### 3.2 用户申请令牌

```
POST /api/v1/vouchers/{id}/seckill-tokens
  ├─ 校验券存在 + 时间窗口
  ├─ 限流:5 次/秒/用户
  ├─ 已购检查:SISMEMBER users userId
  │     已买 → 7004
  ├─ 生成 token(UUID)
  └─ SET clp:seckill:token:{token} = userId,TTL 60s
```

### 3.3 用户秒杀

```
POST /api/v1/vouchers/{id}/orders
Header: Idempotency-Key
Body:   { "token": "..." }

  ├─ 幂等抢占 tb_idempotency
  │     ├─ 已 SUCCESS → 直接返回首次 orderNo
  │     └─ PROCESSING → 1005
  ├─ 校验券 + 时间窗口
  ├─ 执行 Lua(原子)
  │     ├─ 0 → 成功
  │     ├─ 1 → 7003 库存不足
  │     ├─ 2 → 7004 重复购买
  │     └─ 3 → 7005 令牌无效
  ├─ 生成 orderNo
  ├─ 写 tb_outbox(PENDING)
  ├─ 幂等标记 SUCCESS
  └─ 返回 202 { orderNo, status: PROCESSING }
```

### 3.4 异步落库

```
Outbox 定时器(每 1 秒)
  └─ 取 PENDING → KafkaTemplate.send → 标记 SENT

Kafka Consumer(3 并发)
  ├─ 解析消息
  ├─ 查 orderNo 是否已存在
  ├─ 不存在 → INSERT tb_voucher_order + DB 库存 -1
  ├─ 标记 Outbox ACKED
  └─ 手动 ACK offset

用户轮询
  GET /api/v1/vouchers/{id}/my-order
```

## 4. 每一层为什么这么做

### 4.1 为什么要"令牌",不能直接抢?

如果只有一个接口,用户拿到请求就直接扣库存,会带来两个问题:

1. **无效流量直接打到扣减链路**:没资格的人也会触发 Lua。
2. **无法做前置资格校验**:比如活动没开始、用户已购买。

令牌把流程拆成两段:

```
第一段:申请令牌   → 轻量校验 + 限流 + 资格检查
第二段:凭令牌抢购 → 只做原子扣减
```

**令牌必须是:**

- **一次性**:Lua 里 `DEL` 掉,防止一个令牌多次使用。
- **短有效期**:60 秒,过期作废。
- **绑定用户**:Redis 里存的是 `userId`,Lua 校验 `tokenUserId == ARGV[1]`。

> 面试追问:"令牌存在哪?丢了怎么办?"
> 答:存 Redis,60 秒 TTL。丢了就重新申请;令牌只是"入场券",不承担最终正确性。

### 4.2 Lua 脚本逐行讲解

```lua
-- KEYS[1] 库存 key          clp:seckill:stock:{voucherId}
-- KEYS[2] 已购用户 Set      clp:seckill:users:{voucherId}
-- KEYS[3] 令牌 key          clp:seckill:token:{token}
-- ARGV[1] 当前用户 ID

-- 1. 校验令牌,并立即消费
local tokenUserId = redis.call('GET', KEYS[3])
if (not tokenUserId) or (tokenUserId ~= ARGV[1]) then
    return 3
end
redis.call('DEL', KEYS[3])
```

**逐行:**

- `GET` 取出令牌绑定的用户 ID。
- 不存在 → 令牌过期/伪造 → 返回 3。
- 不匹配 → 别人的令牌 → 返回 3。
- 校验通过后**立刻删除令牌**——保证一次性。

> 为什么先删令牌,再做后面的检查?  
> 因为令牌是一次性凭证。即使后面发现库存不足,这个令牌也不应该能再用。

```lua
-- 2. 一人一单
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 2
end
```

- `SISMEMBER` 判断用户是否已经在已购集合里。
- 返回 2 → 外层映射成 `7004 重复抢购`。

```lua
-- 3. 库存
local stock = tonumber(redis.call('GET', KEYS[1]))
if (not stock) or (stock <= 0) then
    return 1
end
```

- 库存 key 不存在或 ≤ 0 → 返回 1 → `7003 库存不足`。

```lua
-- 4. 扣减 + 记录用户
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
return 0
```

- `DECR` 扣库存。
- `SADD` 记录用户,供下次 `SISMEMBER` 判断。

**为什么必须放在一个 Lua 里?**

Redis 执行 Lua 时是**单线程原子执行**,中间不会插入其他命令。

如果拆成:

```java
get(stock);      // 读到 1
// 另一个线程也读到 1
decr(stock);     // 两个都扣,变成 -1
```

就会出现超卖。

Lua 把"读 + 判断 + 写"打包成一次原子操作,这是秒杀不超卖的根本。

### 4.3 为什么库存放 Redis,DB 还留一份?

| 层 | 角色 |
|---|---|
| Redis | **决策层**:真正拦截并发,决定谁抢到 |
| MySQL | **审计层**:记录最终结果,用于对账和恢复 |

如果只用 MySQL:

- 每次扣减都要行锁,几千 QPS 直接打爆数据库。
- 连接池、事务、锁等待都会成为瓶颈。

如果只用 Redis:

- Redis 宕机/丢数据,没有恢复依据。

所以:**Redis 负责快,MySQL 负责对**。

### 4.4 一人一单为什么需要两层?

| 层 | 手段 | 作用 |
|---|---|---|
| Redis | `SISMEMBER` + `SADD` | 拦截 99.9% 的重复请求 |
| MySQL | `uk_voucher_user(voucher_id, user_id)` | 最终兜底 |

Redis 可能因为主从切换、数据丢失而失效;数据库唯一索引不会。

**应用层可以出错,数据库约束不会。**

### 4.5 为什么用 Kafka,不直接落库?

秒杀的瓶颈不是"扣库存",而是"写订单"。

- 写订单要开事务、写两张表、可能还有索引维护。
- 几千 QPS 同步写库,数据库扛不住。

Kafka 的作用是**削峰**:

```
瞬时 5000 请求  →  Redis 扣减 5000 次(很快)
                →  只有 100 个成功
                →  100 条消息进 Kafka
                →  消费者按数据库能承受的速度落库
```

**接口返回 202,不是 200:**

- 202 表示"已受理,处理中"。
- 最终结果通过 `my-order` 轮询或 WebSocket 通知。

### 4.6 Outbox 模式:为什么消息不直接发 Kafka?

直接发 Kafka 的问题:

```
Redis 扣减成功
   ↓
Kafka 发送失败(网络/ Broker 宕机)
   ↓
库存少了,但没有订单 → 数据不一致
```

Outbox 的做法:

```
1. Redis 扣减成功
2. 消息先写 tb_outbox(PENDING)
3. 接口返回 202
4. 定时器每秒扫描 PENDING → 发 Kafka → 标记 SENT
5. 消费者处理成功 → 标记 ACKED
```

**好处:**

- Kafka 暂时不可用不影响用户抢购。
- 应用在发送前宕机,重启后定时器会补发。
- 消息有状态机,可观测、可重试。

**消息状态:**

```
PENDING ──发送成功──> SENT ──消费成功──> ACKED
   │
   └──失败──> 重试(指数退避)──> 超过次数──> FAILED
```

**如果写 Outbox 也失败怎么办?**

代码里做了补偿:

```java
catch (Exception e) {
    redis.opsForValue().increment(stockKey);   // 恢复库存
    redis.opsForSet().remove(usersKey, userId); // 移除用户标记
    idempotencyService.release(acquired.getId());
    throw new BusinessException(SYSTEM_ERROR);
}
```

这是"本地事务 + Redis 补偿"的折中方案。

### 4.7 消费端幂等

Kafka 的语义是 **at-least-once**:消息可能重复投递。

所以消费端必须幂等:

```
查 orderNo 是否已存在
  ├─ 存在 → 跳过插入,直接 ACK
  └─ 不存在 → 插入订单 + DB 库存 -1
```

再加上数据库唯一索引:

- `uk_order_no`
- `uk_voucher_user(voucher_id, user_id)`

**即使并发重复消费,也只会有一条订单。**

### 4.8 对账:最后一道保险

```
期望库存 = initial_stock - 已创建订单数
Redis 库存 vs 期望库存
  不一致 → 写 tb_reconcile_log
```

对账任务每分钟跑一次。

**为什么不自动修复?**

- 自动改 Redis 可能掩盖真正的 bug。
- 先记录、告警、人工确认,是更安全的做法。

### 4.9 限流

令牌接口用了固定窗口限流:

```
INCR clp:seckill:token-limit:{userId}:{voucherId}
第一次 → EXPIRE 1 秒
超过 5 次 → 7006
```

**为什么限令牌接口,不限秒杀接口?**

- 秒杀接口有令牌和 Lua 双重保护。
- 令牌接口更轻,更容易被刷,所以放在最前面限。

## 5. 失败场景与兜底总表

| 失败点 | 后果 | 兜底 |
|---|---|---|
| 令牌过期/伪造 | 无法抢购 | 重新申请令牌 |
| Redis 库存为 0 | 7003 | 直接返回 |
| 用户已购买 | 7004 | Redis Set + DB 唯一索引 |
| Lua 执行异常 | 请求失败 | 释放幂等键,允许重试 |
| 写 Outbox 失败 | 库存已扣但无订单 | 补偿 Redis:恢复库存 + 移除用户 |
| Kafka 不可用 | 消息积压 | Outbox 保留 PENDING,定时重投 |
| 消费者处理失败 | 消息重试 | 不 ACK,由 Kafka 重投 |
| 消息重复 | 重复订单 | orderNo / (voucher,user) 唯一索引 |
| Redis 丢库存 | 可能超卖 | 定时对账 + 告警 |
| 应用宕机 | 消息未发 | 重启后 Outbox 补发 |
| 消费后宕机 | 订单已建但 Outbox 未 ACK | 重投时 orderNo 已存在,跳过 |

## 8. 面试怎么讲

**30 秒版本:**

> 秒杀链路做了五层防护:限流、一次性令牌、Redis+Lua 原子扣减、Outbox 可靠消息、Kafka 异步落库。Redis 负责拦截并发,数据库负责最终正确性;一人一单和订单号都有唯一索引兜底;另外有定时对账任务保证 Redis 与 DB 最终一致。

**可能被追问:**

1. 为什么用 Lua,不用分布式锁?
   - Lua 是单次原子执行,没有锁竞争和锁超时问题;性能更高。
2. 令牌有什么用?
   - 前置资格校验 + 限流 + 一次性凭证,把无效流量挡在扣减链路之外。
3. 消息丢了怎么办?
   - Outbox 本地消息表 + 定时补发;消费端幂等;对账兜底。
4. 为什么不用 RabbitMQ?
   - 我们的方向是数据平台,Kafka 更贴合;秒杀场景 RabbitMQ 也完全可行,取舍不同。
5. 怎么保证不超卖?
   - Redis Lua 原子扣减 + DB `stock > 0` 条件更新 + 对账。

## 9. 常见坑

1. **把令牌当成最终凭证**:令牌只是入场券,最终以 Lua 扣减结果为准。
2. **Lua 里漏掉 DEL 令牌**:令牌可重复使用,一人多单。
3. **只靠 Redis 做一人一单**:Redis 丢数据就失效,必须有 DB 唯一索引。
4. **同步落库**:流量一上来数据库直接被打穿。
5. **直接发 Kafka 不做 Outbox**:发送失败就数据不一致。
6. **消费端不幂等**:Kafka 重复投递直接产生重复订单。
7. **没有对账**:Redis 和 DB 不一致时无人发现。
8. **压测只看 QPS,不看最终库存**:超卖往往在高并发下才暴露。

## 10. 压测实战记录(2026-10-17)

**场景:** 1000 线程、券库存 100、JMeter 与应用同机。

**结果:**

| 检查项 | 结果 |
|---|---|
| Redis 库存 | `0` |
| 订单数 | `100` |
| 去重用户数 | `100` |
| DB 秒杀库存 | `0` |
| 重复订单 | 无 |
| 负库存 | 无 |
| 对账异常 | 无 |

**订单数正好等于库存,没有超卖,没有一人多单。**

### 压测发现并修复的问题:Outbox 状态回写竞态

**现象:** 3 条 Outbox 消息停在 `SENT`,但对应订单已存在。

**原因:**

```
定时器读到 PENDING
   ↓
发送 Kafka
   ↓
消费者处理完成,写入 ACKED
   ↓
定时器拿着旧快照,把状态覆盖回 SENT   ← 竞态
```

**修复:** 定时器的成功/失败回写都加上 `status = PENDING` 条件:

```java
.eq(OutboxMessage::getId, message.getId())
.eq(OutboxMessage::getStatus, PENDING)   // 关键
.set(OutboxMessage::getStatus, SENT)
```

消费者已经 ACKED 时,影响行数为 0,不会被覆盖。

**这个 bug 单测和 5 个用户的功能测试都发现不了,只有高并发才会暴露。**

**结论:** 压测不只验证 QPS,更重要的是验证**最终一致性**和**状态机**。

## 11. 应用侧优化与对比

### 优化前后的路径

| 环节 | 优化前 | 优化后 |
|---|---|---|
| 幂等 | 每请求写一次 `tb_idempotency`;失败再删一次 | Redis `SETNX` 快路径,成功/失败都不写 DB |
| 券信息 | 每请求查一次 `tb_voucher` | Redis Hash 预热,不查 DB |
| 失败请求 | 1000 次秒杀里约 900 次会写/删幂等表 | **零 DB 写** |
| 成功请求 | 写 Outbox | 写 Outbox(保留,可靠性需要) |

### 优化后 1000 线程压测对比

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 秒杀接口平均 | 188.0 ms | 78.7 ms | **-58%** |
| 秒杀接口 P95 | 630.9 ms | 461.6 ms | **-27%** |
| 秒杀接口 P99 | 791.0 ms | 512.0 ms | **-35%** |
| 令牌接口平均 | 89.0 ms | 48.4 ms | **-46%** |
| 令牌接口 P99 | 653.0 ms | 329.0 ms | **-50%** |
| 整体平均 | 138.5 ms | 63.5 ms | **-54%** |
| 整体 P95 | 494.0 ms | 326.9 ms | **-34%** |
| 整体 P99 | 769.0 ms | 495.0 ms | **-36%** |
| 秒杀吞吐 | 215.8/s | 232.8/s | +8% |

### 正确性不变

| 检查项 | 结果 |
|---|---|
| Redis 库存 | 0 |
| 订单数 | 100 |
| 去重用户数 | 100 |
| DB 秒杀库存 | 0 |
| 重复订单 / 负库存 / 对账异常 | 无 |
